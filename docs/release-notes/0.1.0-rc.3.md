# dsh-charter 0.1.0-rc.3

Authority-preserving recovery release. The Charter record is opened through one structured state machine, restored
Sessions with no readable record are never auto-replaced, and owners can export the complete record and restore it to
the same Session lifecycle.

> This file is release-note source material for the GitHub Release; it is outside the npm `files` whitelist and is not
> part of the published tarball. rc.1/rc.2 releases are untouched.

## Install

```bash
dsh plugin --profile web add dsh-charter@next       # newest pre-release
dsh plugin --profile web add dsh-charter@0.1.0-rc.3 # exact, reproducible
```

Channel policy: pre-releases are published under `next`, and we also point `latest` at the newest RC until a stable
release exists. This is our deliberate policy — npm keeps a `latest` tag and we choose its target; it is not an npm
requirement.

## Highlights

- **Source-aware initialization.** `startup` may create the root/fork record; `resume`, `clear`, `compact`,
  `reattach`, and unknown sources stop at `absent-unconfirmed` and write nothing. `session/created` records intent
  only; `agent/created` is authoritative. Ordinary edit never creates a record implicitly.
- **Structured record state.** Host, wire, watch, and Pane share one record-state contract: `healthy`,
  `absent-unconfirmed`, `invalid`, `lifecycle-mismatch`, `unknown`, `write-uncertain`; plus
  `capabilities.recordMaintenance` and `maxRecoveryBytes`.
- **Export / initialize / restore.** Six Remote methods with strict codecs and Session resources. Owners can export a
  complete archive (identity, current snapshot, bounded history, mutation and maintenance receipts), explicitly
  initialize an absent target (twice-confirmed), and restore a validated archive over an absent/invalid target for the
  **same Session lifecycle**. Healthy records cannot be overwritten; cross-Session/cross-lifecycle import is
  unsupported.
- **Bounded maintenance receipts** in version-1 records enable exact replay of initialize/restore after a lost
  response, including restore followed by a later edit; one operation id with different content returns
  `OPERATION_ID_REUSED`.
- **Write-uncertain fencing.** A storage rejection after a possibly durable write publishes no proposed content,
  blocks prompt/tool/edit/initialize/restore/export, emits one structured demotion, never rewrites the key again in the
  same Host lifetime, and converges after restart. Known pre-flight `DomainError`s remain definite outcomes.
- **Per-Session mutation queue** serializes startup init, explicit initialize, edit, and restore with a re-read/CAS at
  every slot.
- **Audit hardening:** read-triggered startup inference is gone (only authoritative `agent/created(startup)` creates
  records; absence/malformed/missing-fork reads never write), restore refuses ambiguous archive operation ids with
  `OPERATION_ID_REUSED`, `maintenanceLimit: 1` trims correctly, shutdown drains mutation queues, startup puts re-read/CAS
  inside the per-Session queue, replay reports the receipt's original revision, and the Storage & recovery UI uses the
  shared admission predicate with localized reasons, resettable two-step confirmations, separate in-flight/unknown
  live-region copy, WebCrypto archive digest verification, and localized export errors.
- **Storage & recovery UI** after Context: record health/revision/lifecycle/digest/over-budget, sensitive export
  download, archive selection + preview, two-step confirmations, absent-unconfirmed and write-uncertain guidance,
  capability/record-limit copy; English/Chinese, light/dark, narrow/keyboard layouts.

## Breaking / downgrade limitation

`recordSchemaVersion` stays `1` and `dsh_charter_v1` is unchanged; rc.3 only adds optional `recentMaintenance`.
This is forward-readable upgrade compatibility, **not rc.2 rollback compatibility**: once rc.3 writes a maintenance
receipt for a Session, rc.2 isolates that Session as schema-invalid (preserved, no injection/editing); upgrading back to
rc.3 restores access. Records without maintenance operations remain readable by rc.2. No migration CLI is required.

## Limitations

- **Missing or unreadable cannot be distinguished.** The storage API does not expose outer-document read errors; the
  plugin reports "missing or unreadable; cannot be distinguished automatically" and does not automatically replace the
  record. For forensic bytes, stop the Host and back up/repair the storage file.
- `maxRecoveryBytes` defaults to 4 MiB (at least `maxRecordBytes + 64 KiB`, 16 MiB hard ceiling). A profile whose record
  budget leaves no room disables maintenance (`recordMaintenance:false`, reason `record-limit`) and requires an
  offline backup after stopping the Host; the existing record limit is never silently lowered.
- Maintenance is owner-only; archives contain user text and must be handled as sensitive. Payload digests detect
  corruption, not malicious provenance. Replay is guaranteed only while the bounded receipt remains in the window.
- Other accepted non-blocking limitations from verification §9 are unchanged (legacy transcript strictness,
  compaction sequence edge cases, WAIT diagnostic wording, artifact-smoke residuals, mutation-receipt retention).
- Manual release actions (annotated tag, push, GitHub Release, `npm publish --tag next`, moving `latest`, public CI,
  fresh-profile UI check) are performed by the release operator, not by the preparation pass.
