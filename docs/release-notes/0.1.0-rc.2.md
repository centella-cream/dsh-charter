# dsh-charter 0.1.0-rc.2

Release candidate / patch for `0.1.0-rc.1`. This file is release-note source material for the GitHub Release; it is
kept outside the npm `files` whitelist and is not part of the published tarball.

- **Version:** `0.1.0-rc.2` (pre-release)
- **Node.js:** `^22.19.0 || >=24.0.0`
- **DSH:** `0.1.7-rc.2`, `0.2.0-rc.1`/`rc.2`, `0.2.1-rc.1`/`rc.2` (see
  [compatibility](../design/compatibility.md); `0.2.1+` is required for per-Peer Remote resource authorization)
- **Artifact:** `dsh-charter-0.1.0-rc.2.tgz`, SHA-256 `69ea612bf82cf0b8c16970fbb6c0ab8d843aae49a999b3e28c03857d532d5bcd`
- **Gates:** `npm test` 20 files / 263 tests, `npm run check`, normal + exact-artifact package smoke, and the
  five-version compatibility matrix (all run for this candidate; see [verification](../verification.md) §8.5)

## Install

```bash
# npm, newest pre-release
dsh plugin --profile web add dsh-charter@next
# npm, exact reproducible version
dsh plugin --profile web add dsh-charter@0.1.0-rc.2
```

Channel policy: pre-releases are published under the `next` dist-tag, and we also point `latest` at the newest RC
until a stable release exists. This is our deliberate policy — npm keeps a `latest` tag and we choose where it
points; it is not an npm requirement. Pin the exact version for reproducible profiles.

## Fixed

- **Pane hook-order crash.** `CharterPane` could throw React's "Rendered more hooks than during the previous
  render" when a Session transitioned `connecting`/null → `ready`, or `error`/null → retry → `ready`: the
  replay-state predicates and the `confirmAbandon` reset effect ran after early returns. They now run above every
  early return, so hook order is invariant across connection states. Rendering and behavior are otherwise
  unchanged.
- **Real rendering regression tests.** Three `react-test-renderer` tests render the actual exported Pane and cover
  connecting/null → ready, error/null → retry → ready, and ready → revision updates. The pre-fix code fails the
  first two with the exact "Rendered more hooks than during the previous render" error; the fixed code passes.

## Security

- Upgrade `zod` from `4.4.3` to exactly `4.6.7`, fixing the high-severity advisory
  [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (memory exhaustion while validating
  oversized constrained collections).
- The dependency tree now resolves a single zod version via `overrides` in the development/test tree
  (`npm ls zod` shows one `4.6.7`); `npm audit --omit=dev` reports **0 vulnerabilities** and the full `npm audit`
  also reports 0 with the deduped tree.
- Because `tsdown` inlines Zod into the browser bundle, the full build/wire tests, client-bundle smoke, package
  smoke, and the five-version DSH matrix were re-run against this build.

## Changed

- Version and current-release documentation moved to `0.1.0-rc.2`; `0.1.0-rc.1` history and evidence are kept.
- Channel policy and install docs now describe the deliberate `next`/`latest` behavior above in README (en/zh),
  user guide (en/zh), and the releasing checklist.
- `0.0.0-stage` on npm is deprecated as a temporary staging placeholder (not a usable plugin release).

## Known limitations

The accepted non-blocking limitations are unchanged and disclosed in [verification](../verification.md) §9
(legacy transcript strictness, compaction sequence edge cases, WAIT diagnostic wording, artifact-smoke hardening
residuals, outer-JSON platform risk, mutation-receipt retention, documentation count drift). In particular, an
unreadable/malformed **outer** JSON charter record is still treated as absent by the JSON storage backend and can
be overwritten; stop the Host and restore from a backup if that occurs. None of these is newly introduced by this
patch.
